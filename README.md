# Mortal AI麻雀コーチ v0.13.0

Mortalの元JSONから局面を抽出し、CodexまたはClaudeを選んで日本語解説を生成します。全評価局面への移動、任意のSQLite保存、全員の河・リーチ宣言牌・副露を使った安全度の質問に対応します。

## システム構成

v0.13.0から、Chrome拡張とローカルサーバーを明確に分離しています。

- Chrome拡張: サイドパネルUI、Mortal画面／レポートJSONの読み取り、局面DTOへの変換、ローカルサーバーとの通信だけを担当
- Node.jsローカルサーバー: 入力検証、局面の正規化、受け入れ・押し引き・点棒遷移・学習ルール、プロンプト構築、CLI実行、SQLite保存を担当
- AI: Codex CLIまたはClaude Code CLIを共通のProvider Gateway経由で実行
- DB: SQLiteをRepository契約の実装として使用

HTTP境界は `/api/v1` でバージョン固定しています。旧版の `/analyze`、`/question`、`/records/*` も互換用エイリアスとして残しています。詳しい依存関係とシーケンスは [ARCHITECTURE.md](ARCHITECTURE.md) を参照してください。

## 初回準備（macOS）

1. Codex CLIをインストールします。
2. ターミナルで `codex login` を実行し、「Sign in with ChatGPT」でログインします。
3. Claudeも使う場合はClaude Codeを導入し、`claude auth login` でログインします。Claudeは任意で、未導入でもCodexは利用できます。
   - 公式インストール例: `npm install -g @anthropic-ai/claude-code`
4. このフォルダの `install-companion.command` をダブルクリックします。Claudeを後から導入した場合も再実行してください。
   - 初回にmacOSがブロックした場合は、右クリックして「開く」を選びます。
5. Chromeで `chrome://extensions/` を開きます。
6. 「デベロッパーモード」をオンにします。
7. 「パッケージ化されていない拡張機能を読み込む」で、このフォルダを選びます。
8. Mortalのレポート画面を再読み込みします。

SQLite保存にはNode.js 22.13以上が必要です。Codexアプリ同梱の対応済みNode.jsがある場合は自動検出します。

macOSではChatGPTアプリ同梱のCodex CLIを優先します。ChatGPTアプリと古い単体CLIが同じモデルキャッシュを読み書きした際の形式不一致を防ぐためです。

Windowsでは `start-bridge-windows.cmd` を使用します。

## 使い方

- レポートを開いてもAI解析は自動開始しません。確認したい選択へ移動して「この局面を解析」を押します。
- 「AIモデル」でCodex / Claudeを切り替えられます。解説・質問履歴・キャッシュはモデル別に分離されます。
- 一度解析した局面はChrome内へ保存され、同じモデル・同じ局面へ戻ると解説を表示します。「この局面を再解析」で更新できます。
- 局面解説は、実打・推奨・判定・Q値差の結論バナー、押し引き補助判定、局面に一致した学習ポイント、60字以内の一言、最大3件の候補比較、折りたたみ詳細として表示します。詳細は「手役・打点面」「手牌構造面」「安全性」「状況判断」のうち、**その局面で実際に差がついた観点だけ**を最大3つ表示します。打点など根拠の無い値は `—` 表示にし、推測しません。
- 結論バナーの括弧内は「実打Q − 推奨Q」で表示するため、実打が劣る場合は `-0.029` のような負数になります。これは点棒損失ではありません。
- パネルの「前の選択」「次の選択」はMortal標準の「Prev Choice / Next Choice」を呼び出し、ミスに限らず前後の意思決定局面へ移動します。一致局面でも質問欄を利用できます。
- 「半荘総評」は「総合評価（A〜D・100点満点）」「ミスの傾向」「今後の改善点」だけを簡潔に表示します。
- 解説下の質問欄では、現在の局面・既存解説・直近の会話だけをCodexへ送り、追加質問ができます。回答は重要な要点だけを1〜3個の箇条書きで返します。
- 質問コンテキストには、局面時点の全員の河、リーチ宣言牌、副露、ドラ表示牌が含まれます。例：「対面リーチに5pの放銃率が高い理由は？」「7sは現物・筋・壁のどれで安全？」
- 質問者本人のプレイヤー番号・自風と、自分／下家／対面／上家の対応を検証済みデータとしてAIへ渡します。他家を「あなた」と呼ばないよう指示しています。
- Mortalの `relative_scores` は自分・下家・対面・上家の順です。レポートごとの `player_id` を使って絶対player ID順へ並べ直し、本人の自風と点数を `verifiedPerspective` に明示します。
- `南1-1 +1000` のように本場・供託が局名へ併記される画面でも、正しい局・本場として認識します。
- 手牌とドラ表示牌は牌種別の枚数をプログラムで集計し、実打・推奨打牌を別の物理牌として二重計上しないようAIへ渡します。
- 実打・推奨・手牌はMortal本体に表示されるため、拡張パネルでは重複表示しません。
- 通常のデスクトップ幅では380pxのパネルを画面右側へ固定し、Mortal本体をわずかに縮小して右端まで表示します。900px以下では操作性を優先してオーバーレイ表示になります。
- 常駐接続の導入後は、ターミナルを開く必要はありません。
- 常駐接続を解除するときは `uninstall-companion.command` を使用します。局面DBは削除せず保存先に残します。

## 局面記録（SQLite）

SQLiteを正本にしています。ObsidianはMarkdownの閲覧・復習に、Notionは共有やダッシュボードに向きますが、局面JSONや質問履歴を重複なく更新・検索する正本にはSQLiteが最も軽く確実です。将来のエクスポートに備え、レポート・局面・質問を分離したスキーマにしています。

ブリッジ起動時に `bridge/migrations/*.sql` を順番に適用し、DBを自動作成します。保存先は次の通りです。

- macOS: `~/Library/Application Support/MortalCodexBridge/data/mahjong-coach.sqlite3`
- Windows: `%APPDATA%\MortalCodexBridge\mahjong-coach.sqlite3`
- Linux: `$XDG_DATA_HOME/MortalCodexBridge/mahjong-coach.sqlite3`（未設定時は `~/.local/share/...`）
- iCloud等の任意フォルダへ保存する場合は、インストール前に環境変数 `MORTAL_CODEX_DATA_DIR` で保存先を指定できます。既存の常駐設定を更新する場合は、現在の保存先を自動的に引き継ぎます。
- 開発・テスト時は `MORTAL_CODEX_DATA_DIR` でフォルダ、`MORTAL_CODEX_DB_NAME` でファイル名を変更可能

旧版の `~/Library/Application Support/MortalCodexBridge/coach.sqlite3` があり、新しいDBがまだ存在しない場合は、初回起動時に内容を新しい保存先へコピーします。

主なテーブルは `reports`、`scenes`、`questions` です。レポートを開いただけでは保存しません。本人以外の牌譜も安全に閲覧でき、パネルの「DBに保存」を明示的に押したときだけ保存を開始します。`scenes.payload_json` にはエクスポート可能な完全な局面JSONを保持します。

### 保存の流れ（v0.8.2）

「DBに保存」は半荘につき1回押すだけです。

1. 押した時点で、その半荘の**全局面**（ミス局面に限らず全ての選択局面）を保存します。生成済みの解説と読み込み済みの質問履歴も一緒に保存します。
2. 以降ボタンは「DB保存済み」のまま変わりません。**局面を移動したりAIモデルを切り替えたりしても「DBに保存」へは戻りません。**
3. 保存済みの半荘で新しく解説を生成したり質問に回答が付いたりすると、**その局面ぶんだけ自動で上書き**します。手動での押し直しは不要です。
4. 「半荘総評」で複数局面の解説がまとめて更新された場合は、全局面を自動で上書きします。
5. 自動保存に失敗したときだけボタンが「DB保存を再試行」に変わり、押して再実行できます。

保存は `scene_id` を主キーにしたupsertです。同じ局面を何度送っても行は増えず、常に最新の内容へ上書きされます。新しい記録に解説が無い場合は既存の解説を消さずに残します。

### iCloud Driveで複数Macと共有する際の注意

SQLiteは同じDBファイルを複数Macから同時に開く用途には向きません。iCloud同期を使う場合は、片方のMacでMortalとブリッジを終了し、`mahjong-coach.sqlite3` の同期完了を確認してから、もう片方のMacで起動してください。競合コピーが作られた場合は、そのまま両方を使い続けず統合が必要です。この構成ではiCloud上で扱いやすい単一ファイル方式を使用していますが、同時利用を安全にするものではありません。

### 財務DBとの分離

麻雀と財務は同じフォルダへ保存して構いませんが、同じSQLiteファイルには混在させないでください。推奨例は次の通りです。

```text
~/MortalData/
├── mahjong-coach.sqlite3
└── finance.sqlite3
```

ファイルを分けることで、バックアップ、共有範囲、暗号化、スキーマ更新、破損時の復旧を用途ごとに管理できます。特に財務DBには別途暗号化とバックアップを推奨します。

### 将来のObsidian / Notionエクスポート

SQLiteを読み取り専用で開き、`scenes.payload_json` と `questions` をMarkdownまたはNotion API用JSONへ変換できます。エクスポーターは正本を書き換えない前提です。この版では正本と保存APIまでを実装し、外部サービスへの自動送信は行いません。

## 保存API

ローカルブリッジは以下を提供します。外部公開はせず `127.0.0.1` のみで待ち受けます。

- `POST /api/v1/records/scenes`: 1件または最大80件の局面、解説、質問履歴をupsert
- `GET /api/v1/records/status`: DBパスとレポート・局面・質問件数を確認
- `GET /api/v1/health`: API・サーバーバージョン、機能一覧、Codex / Claudeの導入・ログイン状態、DB状態を確認
- `POST /api/v1/analyses/scene`: 現在局面を解析（NDJSONストリーム）
- `POST /api/v1/analyses/hanchan`: 半荘総評を生成（NDJSONストリーム）
- `POST /api/v1/questions`: 局面への追加質問（NDJSONストリーム）

ストリームイベントは `status`、`result`、`error` の3種類です。契約定義は `bridge/contracts/` に置き、Chrome側は `extension/clients/bridge-client.js` とService Workerを通してのみ利用します。

## 安全設計

- APIキー、ChatGPTのパスワード、ブラウザCookieを拡張機能へ保存しません。
- Codex CLI / Claude Codeが保持する公式ログイン情報を再利用します。
- Codexは `--ephemeral`、読み取り専用サンドボックス、承認なしの設定で実行します。
- ClaudeはPrint mode、セッション非保存、ツール無効、JSON Schema指定で実行します。
- Claudeへ渡すJSON Schemaは互換性のためメタスキーマ宣言を除外し、検証ルール本体だけを渡します。
- 外部から任意プロンプトを送れないよう、ブリッジは麻雀牌・数値・Mortalの定型フィールドだけを受け付けます。
- 河・副露も同じく牌、プレイヤー番号、定型フラグだけを検証して受け付けます。レポート内の文字列を命令として扱いません。
- 受け入れ枚数は元JSONにないため、AIに推測させず、ブリッジ側で手牌から計算した値だけを渡します。
- 質問履歴はChrome内へ保存し、「DBに保存」を押してその半荘を保存対象にした場合だけSQLiteへ保存します。送信時は直近6件だけを使ってトークン消費を抑えます。

## 確認手順

1. `install-companion.command` を再実行し、更新済みブリッジとマイグレーションを常駐先へコピーします。
2. `chrome://extensions/` で拡張を再読み込みし、Mortalレポートも再読み込みします。
3. レポートを開いただけでは「DBに保存」のままで、`records/status` の件数が増えないことを確認します。
4. 「前の選択」「次の選択」が前後の全評価局面へ移動し、「前のミス」「次のミス」がミス局面間を移動することを確認します。
5. CodexとClaudeを切り替え、任意の局面で「この局面を解析」を押して選択中のモデルだけが生成することを確認します。
6. 「対面のリーチに対して、この牌の危険度は？」と質問し、質問者本人と対面を取り違えず、河・宣言牌・副露に基づく回答になることを確認します。
7. 「DBに保存」を押した後だけ「DB保存済み」になり、`http://127.0.0.1:38765/api/v1/records/status` の件数が増えることを確認します。
8. 保存後に「次の選択」「次のミス」で局面を移動しても「DB保存済み」のままで、ボタンが「DBに保存」へ戻らないことを確認します。
9. 保存後に新しい局面を解析し、ボタンが「DB保存済み」のまま `/api/v1/records/status` の局面件数が増えない（＝重複せず上書きされている）ことを確認します。
10. 本場・供託のある局（例：`南1-1 +1000`）でも「この局面を解析」が有効になることを確認します。

開発者向けの自動テストは、対応Node.jsで拡張フォルダから次を実行します。

```sh
node --test bridge/*.test.mjs
```

## トークン効率

通常の局面解説は「この局面を解析」を押した場面だけ生成します。不要な局面を一括生成しないため、確認したい選択だけに利用枠を使えます。「半荘総評」を押した場合のみ、不一致局面をまとめて送信します。

## 生成仕様

- 表示は「理由」「教訓」の2項目だけです。
- 字牌は東・南・西・北・白・發・中の漢字表記に統一します。
- 局面解説は牌効率だけでなく、混全帯么九・混一色・三色などの役と打点ルートを先に比較します。
- Q値・確率・損失・シャンテン数はMortal JSONから確定
- AIが確認できない内容は注意欄に分離

### 押し引き・安全性の数値根拠（v0.8.0）

局面JSONへ、ブリッジ側でMortalの生データから機械計算した以下の値を追加し、AIが「なんとなく」ではなく具体的な数値で押し引きを言語化できるようにしています。AIはこれらの値を正本とし、独自に暗算しません。

- `standings`: 4者の素点から算出した現在の着順・トップ差・ラス差
- `position.gameLength` / `isLastKyoku`: 東南戦の判定とオーラス（南4局）かどうか。ゲーム長が判定できない場合は`null`のまま断定しません
- `position.turnPhase`: 巡目から判定した「序盤/中盤/終盤」
- `table.players[].safety`: 各他家の河から機械計算した現物・筋
- `table.visibleCounts`: 手牌・河・副露・ドラ表示牌を合算した牌種別の見えている枚数（壁の判定材料）
- `verifiedTileCounts.dora`: 自分の手牌中の表ドラ・赤ドラ枚数（裏ドラは含みません）
- `table.kyotakuSticks`: 現時点の供託（リーチ棒）本数
- `alternatives[].probability`: Mortalの方策選択確率であり、和了率・放銃率ではないことをプロンプトで明示

半荘総評（`summary.system.md`）も各局面の`standings`を参照し、「ラス目での安全策」「トップ目での無理な押し」のような着順を踏まえた押し引きの傾向を優先的に拾うようにしています。

### 説明可能な押し引き判定層（v0.10.0）

局面解析時に、MortalのQ値とは独立した補助判定をブリッジで計算します。結果画面には「押し／やや押し／比較保留／ややオリ／オリ」と、攻撃・守備の根拠を表示します。

- 攻撃材料：推奨打牌後のシャンテン、受け入れ、手牌中のドラ、親番、フリテン、終盤、オーラスの着順
- 守備材料：他家のリーチ、副露数、副露後の手出し、巡目、推奨牌の現物・スジ・字牌の見え枚数、オーラストップ目
- 副露イベントへ「その時点の本人の河枚数」を保存し、副露後のツモ切り／手出しを区別します
- 候補表の実打・推奨牌の危険表示は、AIの作文よりブリッジの計算結果を優先します
- 判定結果と根拠は解析結果に添付され、DB保存を押した場合は局面JSON・解説と一緒に保存されます

この判定は公開情報を比較する**説明用ヒューリスティック**です。表示する材料点は放銃率・和了率・局収支・期待値ではありません。正確な点棒期待値と着順遷移は、和了打点・放銃打点の計算器を追加する次段階で実装します。

確認手順：リーチ者がいる遅い手で「オリ」側になること、現物を推奨された場合に候補表が「現」になること、2副露後に手出しが続く相手を根拠として表示することを確認してください。

### 打点・点棒・着順遷移（v0.11.0）

押し引きカードの下に「点棒・着順シミュレーション」を追加しました。

- 翻・符・親子・ロン／ツモ・本場・供託から、100点単位の切り上げと満貫以上の上限を含む打点を計算する基盤を追加
- 現在の4人の点棒へ任意の増減を適用し、同点を含む着順を再計算
- 相手の手牌・翻符が見えない局面では、**3900点・8000点・12000点だった場合**の自分のロン和了／放銃後の点棒と順位を条件別に表示
- 本場は放銃者から300点／本、供託は和了者へ1000点／本として別表示
- 局開始点から成立済みリーチ者の1000点を差し引き、現在局面の実点棒へ補正してから計算（供託の二重計上を防止）
- 牌譜の次局開始点がある場合は、それを正本として「実際の局結果」と終了後の点棒・着順を表示
- 実際の局結果は未来情報なので、通常の局面解説を生成するAIには渡さず、UIの事後検証にだけ使用
- DB保存時は局面の終了情報と計算済みシミュレーションも一緒に保存

固定打点の各行は、相手の実際の打点や発生確率を推定したものではありません。正確な和了見込み打点を自動表示するには、テンパイ形の分解・役・符の判定を追加する必要があります。

確認手順：現在点・本場・供託を確認し、3900点放銃行の減点が「3900＋本場」になっていること、ロン和了行では供託が自分の加点だけに含まれること、実際の局結果が次局の開始点と一致することを確認してください。

### 牌効率・守備の学習ルール（v0.12.0）

てりやき麻雀教室の牌効率カテゴリ11記事・守備カテゴリ4記事を確認し、本文を保存・転載せず、「結論・適用条件・例外・出典」へ要約したルール台帳を `bridge/tactics-knowledge.mjs` に追加しました。

局面ごとに次を機械照合し、該当したものだけを「この局面の学習ポイント」とAIの解説コンテキストへ渡します。

- シャンテンが悪化する候補は、見かけの受け入れ枚数が多くても優先しない
- 同じシャンテンでは、河・副露・手牌・ドラ表示牌を差し引いた実残り受け入れを比較する
- 受け入れが近い場合は、最終形・打点・安全度の比較へ進む
- テンパイ時は待ちの種類数と場に残る枚数を表示する
- リーチ・高警戒の仕掛けに対して、手の距離と現物・スジ・壁を組み合わせる
- 4枚壁は両面待ちだけを否定し、単騎・双碰・嵌張などが残るため完全安牌とは扱わない
- スジ・河読みは相対比較に限り、待ちや放銃率を断定しない

Mortalの推奨、計算済みのシャンテン・受け入れ・見えている枚数を正本とし、記事の定石だけで最善打を上書きしません。二度受け・5ブロック・待ち形は、現版で形を厳密計算できない局面ではAIに推測させない設計です。

### 生成が長い場合の接続維持（v0.8.1）

Chrome拡張のservice worker（Manifest V3）は約30秒間イベントが届かないと停止し、生成中の接続ごと切断されます。Codexは途中経過を随時出力しますが、Claudeは完了まで一切出力しないため、Claudeを選ぶと解説がエラーになることがありました。以下で解消しています。

- ブリッジが生成中10秒ごとに経過秒数入りの進行状況を送り、接続を維持します（Codex / Claude共通）
- 3分を超えても完了しない場合は、接続を放置せず日本語のタイムアウトエラーを返します
- Claudeの実行モデルとeffortはv0.9.0で見直しました（下記「応答時間とトークンの削減」を参照）

### 拡張を更新したときの「Extension context invalidated」（v0.8.3）

`chrome://extensions/` で拡張を再読み込み・更新すると、開いたままのMortalページに残っている**更新前のcontent.js**は無効になります。この状態で古いスクリプトが `chrome.*` を呼ぶと `Uncaught (in promise) Error: Extension context invalidated.` がコンソールへ出ます。データが壊れる類のエラーではなく、**ページを再読み込みすれば解消します**。

v0.8.3では、この失効を検知したら以下のように静かに停止するようにしました。

- 15秒ごとの接続確認と、局面変化の監視を停止します（エラーが出続けません）
- 接続ボタンが「ページを再読み込み」に変わり、押すとページを再読み込みします
- `chrome.storage` / `sendMessage` は `chromeCall()`、生成用ポートは `openStreamPort()` を通してのみ呼び出し、失効時は例外を投げずに終了します

### 解説を麻雀の言葉だけで書かせる（v0.8.4）

v0.8.0で数値根拠を渡した際、プロンプトで「該当フィールドを引用する」と指示していたため、AIが `omote:1` `standings` `selfRank:1` `table.players` のような**内部フィールド名をそのまま解説文へ書いてしまう**問題がありました。

3つのプロンプト（局面解説・質問回答・半荘総評）すべてに「読者に見せる言葉の原則」を追加し、内部データを麻雀の言葉へ言い換えるよう変更しています。

- 禁止する識別子を列挙し、バッククォートやコロン付きの値表記（`omote:1` 等）も禁止
- 内部データ→出力表現の対応表を明示（例：着順と点差は「トップと7000点差の2着目」、現物・スジは「下家の現物」「対面に対してスジ」）
- データが無い観点は「フィールドが空」ではなく麻雀の事実として書く（例：1巡目なら「まだ全員の河が空で危険度を測る材料が無い」）
- 出力前の自己検証チェックにも、識別子・記号が残っていないかの項目を追加
- 質問回答の「根拠」欄も、内部パス（`scene.table.players[2]`）ではなく盤面の事実（「対面の河に4pと7pが無い」）を書く仕様へ変更

### 受け入れ枚数の自前計算と、観点の自動選択（v0.9.0）

Mortalの元JSONには受け入れ枚数が入っていないため、候補比較表の「受入」が常に `—` でした。手牌からシャンテン数と受け入れを自前で計算するようにしています（`bridge/shanten.mjs`）。

- 標準形・七対子・国士無双のシャンテン数を計算（副露がある場合は標準形のみ）
- 打牌候補ごとに「切った後のシャンテン数」「受け入れ牌と残り枚数」「受け入れ合計」を算出
- 残り枚数は自分の手牌・全員の河・副露・ドラ表示牌に見えている分を差し引いた枚数
- **シャンテンが悪化する候補は受け入れ枚数が増える**ため、最小シャンテンを保てるかを `keepsShanten` で明示し、枚数だけで比較させない
- 14候補ぶんの計算でも十数ミリ秒で終わる

あわせて、**毎回4観点を並べるのをやめました**。その局面で実際に差がついた観点だけを解説します。判定はブリッジ側で数値から行います。

| 観点 | 選ばれる条件 |
|---|---|
| 手牌構造面 | シャンテンが落ちる、または受け入れ枚数に差がある |
| 安全性 | リーチ者がいる、2副露以上の他家がいる、終盤 |
| 手役・打点面 | 手牌にドラがある、供託がある |
| 状況判断 | オーラス、または着順が動く点差 |

重要な順に最大3つまで選び、AIはその見出しだけを書きます。無関係な観点を並べないぶん、読みやすく生成も速くなります。

### 応答時間とトークンの削減（v0.9.0）

受け入れ枚数・危険度・着順・観点の判定をすべてブリッジ側で計算するようになり、Claudeの仕事は「計算済みの数値を日本語へ言い換える」ことに絞られました。重い推論が不要になったため、`--model claude-sonnet-5` と `--effort low` で実行します。

同じ局面での実測は次の通りです。

| 版 | モデル / effort | 応答時間 | 見出し数 | 解説の文字数 |
|---|---|---|---|---|
| v0.8.1 | 既定 / 既定(high) | 約122秒 | 4 | 約670字 |
| v0.8.2〜0.8.4 | 既定 / medium | 約59秒 | 4 | 約600字 |
| v0.9.0 | Sonnet 5 / low | **約20秒** | **2**（差がついた観点のみ） | **282字** |

## 一般公開する場合

Chrome拡張単体にはローカルプログラムを起動する権限がありません。一般公開版では、拡張とは別に署名・公証したコンパニオンアプリを配布し、Native Messagingで接続する構成を推奨します。各利用者はコンパニオン側で `codex login` を行い、自分のChatGPT契約と利用枠で生成します。
